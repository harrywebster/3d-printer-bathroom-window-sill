# CLAUDE.md — working rules for this repo

Rules for this project, replicated from the workflow used on
[3d-printer-tepe-easy-pick-toothpicks-case](https://github.com/harrywebster/3d-printer-tepe-easy-pick-toothpicks-case).
Most of that project's rules exist because something failed there. This is a
first revision, so most of the invariants below are written from first
principles (why it would matter if broken), not from a failure history yet.

## Every revision, without being asked

1. Bump the version: copy `src/geomNN.py` to `geomNN+1.py`, change parameters
   there. Never edit a released revision in place.
2. Run the single command — it is the only path to shipped files:
   ```
   make v1
   ```
   which is `python3 src/build.py geom01 v1` into `build/v1/`, then
   `src/ship.py` copying that into `revisions/v1/` and the root aliases.
   `ship.py` only ever copies; it never regenerates anything.
3. The build regenerates **all** of: product-render PNG, schematic PNG,
   README.md, colour 3MF, one STL per tile. Never generate one without the
   others — the point of one script is that the pictures shown for sign-off
   and the files that get printed can never come from different geometry.
4. Shipping refuses to overwrite an existing `revisions/vNN`. If you hit that
   guard, the answer is almost always to bump the version, not `FORCE=1`.
5. Present the newly built files for sign-off before they are treated as
   done — the product-render PNG and the schematic PNG **first**, before the
   STL/3MF are treated as final. This project explicitly separates concept
   sign-off (`make build-v1`, pictures only, nothing shipped) from a shipped
   revision (`make v1`). Don't skip straight to shipping.

`make verify` rebuilds whatever the root currently ships and diffs it,
without shipping anything. Run it after changing a dependency or on a fresh
machine.

> **Why one script.** The toothpick-case project lost two revisions to a
> hand-edited import line that pointed the exporter at stale geometry while
> the pictures had already moved on. The same class of bug is easy to
> reintroduce here (five tiles, several boolean stages) if any deliverable is
> ever generated by a path that doesn't also touch the others.

## Verification is part of the build, not a manual step

The build asserts and records these in the README:

| Check | Requirement |
|---|---|
| Each tile mesh | closed, one body |
| Shipped 3MF reloaded vs model volume | must match |

Compare meshes by volume and bounds, never byte-for-byte. The boolean
library tessellates flat regions a few triangles differently between runs;
that changes how the shape is written down, not the shape. `src/verify.py`
does it this way. A real regression moves a volume or a bound.

## Dependencies

`requirements.txt` is pinned, because the README quotes volumes and the
checks compare them — a different manifold3d/trimesh version could
tessellate a boolean result with a measurably different volume. `scipy`,
`lxml`, `rtree` and `networkx` are listed even though nothing imports them
directly — trimesh loads them for convex hulls, 3MF reading, proximity
queries and `body_count`. Without them the build dies part-way through,
*after* writing some of the deliverables. Don't prune them.

The venv is created and populated with `uv`, not `pip` — this environment's
`.venv` has no `pip` module installed into it, only what `uv` puts there.
`make deps` calls `uv pip install --python .venv/bin/python`, not
`pip install`.

## Writing rules

- The README opens with **why the board was built**, then what it is.
- Never use "watertight" in user-facing text. It is the mesh-topology term
  and reads as a waterproofing claim about the physical object. Say "closed
  mesh, one body".
- Every number in the README and the schematic is interpolated from the
  geometry module at build time. No hand-typed dimensions — they go stale
  the moment a constant changes.

## Design invariants — don't break these silently

- **Flat underside.** No chamfer or feature on the bottom face; it is the
  thing that meets the sill. *Why it matters: any bottom-face feature breaks
  full contact with the sill, so the board rocks or the slope reads
  differently than modelled.*
- **The wedge slope only applies across `SILL_D` (220 mm).** The nose beyond
  it tapers on its own, shallower slope down to `THICK_TIP`. *Why: the nose
  is unsupported by the sill, so it needs to stay thin and light rather than
  following the same fall as the resting section, or the cantilever gets
  heavier for no drainage benefit.*
- **Ribs are a true semicircle (`RIB_W == 2*RIB_H`).** That lets a rib be
  built as a flat-bottomed half-cylinder and sheared onto the slope with one
  affine transform, instead of hand-building a slope-following profile per
  rib. *Why: change `RIB_H` without keeping `RIB_W == 2*RIB_H` and the shear
  trick in `geom01.py` (`_rib_profile` / `shear_to_slope`) stops producing a
  rib that actually sits flush on the surface.*
- **Ribs stop at `SILL_D`.** No ribs on the nose or inside the plant pad
  footprint (plus a `PAD_APRON` margin). *Why: the nose is a thin cantilever
  where fine ribs add print time without helping drainage, and ribs under
  the pad would show through / interfere with a flat saucer.*
- **Magnet pocket y-positions are chosen for wall thickness, not evenly
  spaced.** The literal brief asked for a pocket "near y=200"; at y=200 the
  wedge has tapered to 5.1 mm, too thin to hold a 6.2 mm pocket without
  breaching both faces. `MAG_Y` uses 165 instead, which keeps ~7.0 mm of
  material. *Why: check this again any time `THICK_BACK`, `THICK_FRONT` or
  `MAG_D` change — the safe range for the "front" pocket moves with them.*
- **Tongue/groove and magnet pockets run only across `SILL_D`, not onto the
  nose.** *Why: keeping the joinery in the constant-purpose sill zone avoids
  it interacting with the nose's independent taper and drip groove.*
- **`N_TILES x TILE_W == TOTAL_W` exactly (5 x 170 = 850).** Nothing rounds
  or pads between tiles. *Why: any gap between tiles is either a visible
  seam gap or a dimension the tongue/groove clearance has to silently
  absorb — better to keep the arithmetic exact and let `TONGUE_CLR` be the
  only intentional slack in the system.*
- **`EMBED` (0.05 mm) overlaps every unioned/sheared feature into the body
  it touches.** *Why: manifold3d booleans on two meshes that meet at an
  exactly coincident face are the single most common source of a
  non-watertight or multi-body boolean result. A small guaranteed overlap
  side-steps it entirely.*
- **Outer footprint (`TOTAL_W`, `SILL_D`, `TILE_W`) lands on whole
  millimetres**; the wedge thickness and pad height are the derived
  quantities that come out however the maths gives them.

## Printing

Bambu Lab A1, 0.4 nozzle, 0.20 mm layers, no supports. PLA Basic Grey.

Each tile prints flat as modelled (z=0 is the underside, already the print
bed face). Only one or two tiles fit the 256 x 256 mm bed at a time — the
3MF lays all five out with a visual gap for reference; reposition them in
the slicer before each print run.

Nothing in the model should trigger an auto-support suggestion: the nose is
a shallow taper rather than a bridge, and the drip groove is a small
undercut on the underside, not an internal cavity. If the slicer proposes
support anywhere, something is wrong with the orientation, not the model.

G-code is not generated or kept in this repo. It is specific to the printer,
filament and calibration state, so slice it locally from the 3MF each time.
